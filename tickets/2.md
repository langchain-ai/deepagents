# Ticket 2: preserve and order incoming messages

- Status: implemented
- Priority: P1
- Component: `deepagents-talon`
- Planned PR: `fix(talon): preserve incoming messages across turn replacement`
- Review findings: 2 (lost inputs) and 3 (delayed inputs overtaking `/stop`)

## Problem

`TalonHost._replace_agent_turn` starts a task for each incoming message and cancels the previous task. If two messages arrive before the first task runs, the first input never reaches the runtime or its checkpoint. This occurs naturally when a channel dispatches multiple messages from one polling batch.

Separately, channel adapters prepare attachments and sometimes retrieve context before dispatching messages to the host. Concurrent preparation can reorder inputs: a later `/stop` is handled before an older attachment finishes downloading, and that attachment subsequently starts a new turn. The host's conversation lock cannot restore ordering that was already lost upstream.

These failures can discard a user's constraints or start work after the user has tried to stop it.

## Reproduction

Both behaviors were reproduced locally without live channels or model APIs:

1. Deliver `Only work in the staging environment.` and then `Now run the cleanup.` to the same host conversation without yielding between deliveries. Only the second text reaches the runtime.
2. Hold Slack attachment preparation with an event, deliver a later `/stop`, and release preparation. The older message starts a turn after the stop command has been processed.
3. Hold a WhatsApp bridge media download while enqueueing a later `/stop`. The bridge queues the stop before the older attachment.

## Implementation scope

- Record an admitted input's identity and conversation order before asynchronous preparation. Keep every accepted user input until it is committed to conversation state or explicitly cancelled by a control command.
- Replace active computation without losing the inputs it was meant to process. Handle bursts and already-checkpointed inputs without duplication.
- Make `/stop` invalidate earlier queued or preparing work as well as active turns. Prevent pre-reset preparation from entering a conversation created by `/new` or history reset.
- Keep stop/control handling responsive while preparation is stalled, and keep unrelated conversations independent.
- Preserve sender authorization, approval replies, OAuth interception, and generation checks. Bound pending work and define what happens when admission capacity is exhausted.
- Use one input lifecycle across adapters. Coordinate WhatsApp admission changes with [ticket 3](3.md).

## Acceptance criteria

- [x] Consecutive accepted messages retain both texts, in order, even if the first turn has not started.
- [x] Replacing a turn after its input was checkpointed does not duplicate that input.
- [x] An older attachment finishing after `/stop` cannot start an agent turn; genuinely later input can.
- [x] Delayed preparation cannot cross `/new` or history-reset boundaries.
- [x] A stalled conversation does not block another conversation or its control commands.
- [x] Deterministic tests use events/barriers rather than timing assumptions, including the WhatsApp bridge ordering case.

## Implementation and verification

Implemented in the local Talon package. Channel handlers now admit authorized envelopes
before deferred context, media, and transcription work. The host retains bounded,
ordered inputs with stable identities across turn replacement. The runtime commits
those inputs before model execution and acknowledges the checkpoint through an optional,
keyword-only `AgentRequest.inputs_committed` callback. Checkpoint identities also cover
cancellation between persistence and acknowledgement.

Stop and reset commands discard earlier pending inputs and cancel preparation without
waiting for downloads. Preparation completion cannot enqueue a replacement turn. Normal
turn replacement reuses in-flight preparation. Failed preparation retains the input;
capacity rejection is explicit. Existing plain channel callbacks remain supported.

The WhatsApp bridge now emits envelopes synchronously and exposes authenticated,
identity-bound `POST /prepare`. Python exposure checks precede preparation. This supplies
ticket 3's two-stage admission boundary; aggregate retained-media quotas and comprehensive
abandoned-download cleanup remain ticket 3 work. Externally managed bridges must be
updated for the new ordering guarantee. Limits and token expiration are documented in
the Talon README.

Validation: 503 distinct Python tests passed across the host, runtime, channel,
approval, OAuth, history-reset, archive, background, and new input-lifecycle suites;
34 bridge tests passed. `make lint` (Ruff and ty) and `git diff --check` passed.
The new regressions use events/barriers, including a real LangGraph checkpoint and
stalled Slack/WhatsApp preparation. No live channel or model API was used.
