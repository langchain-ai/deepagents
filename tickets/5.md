# Ticket 5: serialize cron-store mutations

- Status: implemented
- Priority: P2
- Component: `deepagents-talon`
- Planned PR: `fix(talon): serialize cron store mutations`
- Review finding: 7

## Problem

`CronJobStore` reads the complete job list, changes it, and atomically replaces `jobs.json`. There is no lock around the complete read-modify-write operation. Atomic replacement prevents a partially written file but cannot prevent a stale writer from overwriting another successful mutation.

Synchronous LangChain tools run in executor threads. Multiple tool calls, different conversations, background workers, and scheduler operations can therefore reach the same store concurrently within one Talon process. The implementation's single-writer assumption is already violated without running a second host.

Consequences include lost job creations, overwritten edits, and stale writes restoring removed or disabled jobs. The cached list and file identity can also become inconsistent under concurrent writes.

## Reproduction

1. Create one `CronJobStore` in a temporary directory.
2. Start two job creations in separate worker threads.
3. Use a barrier immediately before their writes so both have read the original list.
4. Allow both writes to finish.
5. Both creations return success, but reading `jobs.json` through a fresh store reveals only one job.

This race was reproduced locally with harmless prompts and no scheduler execution.

## Implementation scope

- Serialize each complete mutation, including its read, validation, replacement, and cache update. Locking only `_write_jobs` is insufficient.
- Cover creation, editing, removal, claiming the next run, recording run results, discarding finished jobs, and retention pruning.
- Keep readers and the cached file identity coherent with committed writes. Avoid deadlocks when public methods call shared read/write helpers.
- Use a thread-safe mechanism appropriate for synchronous tool calls and scheduler access. Prefer standard-library or existing repository mechanisms; a new database or dependency is not required to fix the demonstrated race.
- Keep locks out of agent execution, channel delivery, and other long-running work. Preserve existing conversation scoping and atomic-file durability/permissions.
- Define the ownership model explicitly. If multiple store instances for the same path are supported, coordinate them too; do not imply cross-process safety from an instance-local lock.

## Implementation and verification

Implemented on `jk/talon/ticket-5`. Stores sharing a resolved directory use a
shared reentrant lock around reads and complete mutations, including cache
updates. Coordination is within one process; each store file must have one owning
process. Agent execution and channel delivery remain outside the lock.

Concurrency tests cover one store and multiple instances, all mutation types,
exclusive claims, fresh and cached reads, failure recovery, and asynchronous
LangChain tool calls. A test-only lock wrapper signals after the competing caller
fails a nonblocking acquisition while the first writer is paused. Only then is
the writer released; timeouts guard against hangs rather than determine overlap.
Assertions still verify the saved records through fresh disk reads.

Validation: `make test` with `tests/unit_tests/test_cron_concurrency.py`,
`tests/cron/`, and `tests/unit_tests/test_pairing.py` passed all 197 Python tests
and 31 bridge tests. `make lint` passed Ruff checks, formatting, and type checking.
